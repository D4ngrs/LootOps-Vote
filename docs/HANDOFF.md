## What this is

`LootOps-Vote` (`https://github.com/D4ngrs/LootOps-Vote`, live at `https://d4ngrs.github.io/LootOps-Vote/`) is a fork of `LootOps` (`https://github.com/D4ngrs/LootOps`, untouched, stays manual-entry-only). It adds a Discord vote-to-roll workflow: post an item list to Discord, people react to claim interest, then the results get rolled automatically. `index.html` is the whole frontend (single file, ~4,900 lines, inline HTML/CSS/JS, no build step). `worker/src/index.js` is the Cloudflare Worker backend, deployed at `https://lootops-vote-worker.lootopsd4.workers.dev`. Currently at **`APP_VERSION = 'v0.9.0'`**, shipped this session — the user deliberately held it at `0.9.0` rather than `1.0.0`, reasoning that a real production loot session on the org's actual Discord server (not the current personal test server) is the more meaningful "graduation" moment than a code milestone.

## Known codebase gotchas (all rediscovered the hard way this session — don't repeat)

1. **There is no generic `.hidden{display:none}` rule in this codebase.** Every single hideable element needs its own explicit `#id.hidden{display:none}` (or `.class.hidden{...}`) rule — `classList.add('hidden')`/`.toggle('hidden', ...)` alone does *nothing* visually unless that rule exists. Bit twice this session: `#voteStatus`/`#unwantedItemsPanel` (caught before shipping), and the entire flavor-presets modal (shipped broken, fixed after the user reported the list/edit views rendering stacked on top of each other). **Grep for existing `.hidden{` rules and add a matching one for any new toggleable element, every time.**
2. **`flex: 1 1 auto` does not reliably make an item fill available space; `flex: 1 1 0` (or the `flex:1` shorthand, which defaults basis to `0%`) does.** With `auto` basis, the browser sizes the item to its own intrinsic content first and *then* grows — for something like a near-empty `<textarea>`, that intrinsic size can be much smaller than expected, so it looks like flex-grow "isn't working" even though it technically is.
3. **Shared CSS classes silently carry constraints across unrelated uses.** The preset-edit textarea also carries the `.flavor-textarea` class (for base styling reuse) — but `.flavor-textarea` sets `max-height:280px` for the *small* inline flavor box, which silently clamped the *big* 920px-tall preset editor regardless of flex-grow, since `max-height` always wins as a hard clamp. Always check what a reused class brings with it, not just what you're adding on top.
4. **Testing with an invalid/fake session token in the browser causes an unpredictable background page reload mid-test.** This is now *also* real production behavior for anyone logged out (see item 25 above), not just a test artifact — but for testing specifically: if the session is invalid, `workerFetch`'s handler does `clearSession(); location.reload();`, which races with any multi-step manual test script split across separate tool calls, wiping state between calls and producing confusing, non-reproducible-looking failures. **Always do multi-step DOM verification in one single atomic script execution** immediately after page load (or use a real valid session), never split across calls with a fake token.
5. **GitHub Pages build status occasionally reports `"errored"` transiently before settling on `"built"`** for the same commit — keep polling a couple more times rather than assuming a real failure.
6. **Any code that calls `workerFetch` (or otherwise expects a session) at page-load time must be gated behind `isSessionValidLocally()` first.** Not doing this is exactly what caused item 25's bug — it's tempting to just call a "check something" function unconditionally on load, but the login gate being client-side means that code runs whether or not anyone's actually logged in.
7. **Never write user-facing prose (changelog entries, new UI text, new confirm-dialog messages, etc.) without checking it for em dashes before shipping.** This is a standing, explicit user preference (see the `feedback_no_em_dash` memory) that's easy to forget when writing *new* copy — the original sweep only caught text that already existed in the file.

## Open decision: possible move off single-file `index.html`

Still not started, no plan/spec written — this is exactly where the previous handoff left it. Recap: the user asked about migrating to Astro (partly on a friend's recommendation, and for "industry standard" credibility); recommendation given was against it specifically (Astro's islands/hydration model doesn't fit an app that's almost entirely interactive — would mean rewriting ~4,900 lines of imperative DOM code into a component framework's reactivity model just to get a build step, high regression risk against the entire feature list above) in favor of a **plain ES-module split**: same code, reorganized into `.js` files by responsibility (boot, auth, items, names, roll logic, history, share, loot sheet, presets, Discord/vote integration, wiki search) using native browser `import`/`export`, no framework, no bundler, no build step, deployed exactly as today.

The user then clarified their actual motivation: **organized code, and less for Claude to "read up" on** (i.e. not having to re-read/re-grep a single ~4,900-line file every time) — a maintainability goal, not a rendering/performance/SEO one. That confirms the plain-module-split recommendation is the better fit; Astro doesn't really solve either stated problem. Estimated Astro at ~15-25 focused sessions for full parity; the plain module split at ~3-6.

**No direction has been confirmed yet — the user was still weighing it when this handoff was written.** If picked back up, this is a brainstorming-skill-worthy decision (real architecture change, even if "just" a reorganization) before any code moves — map out the module boundaries and shared-state handling (a lot of functions currently rely on implicit shared top-level script scope — `namesArr`, `itemsArr`, `lastRollResult`, etc. — which becomes explicit imports/exports) before touching anything.

  - **Multi-qty solo-voter over-award** (`consumeVoteResults`, `index.html`): design decision made with the user — a lone voter now gets exactly **1** unit of an item regardless of its `qty`; any remaining copies (`qty - 1`) are pushed into the existing Unclaimed Items pipeline (same shape as a zero-voter item, so it's visible and reimportable). Verified live via a fabricated vote record run through `consumeVoteResults` in Sandbox Mode (bypasses Discord/Worker entirely).
  - **Unrelated but worth knowing**: shipping this hit a genuinely slow/stuck GitHub Pages deploy — the `pages-build-deployment` workflow's `build` job always finished in ~20s (fine), but the `deploy` job (GitHub's own Pages activation backend) sat at `deployment_in_progress` for the full 10-minute action timeout and failed outright once, then took several more minutes on a manually re-queued attempt (`POST /repos/{owner}/{repo}/pages/builds`) before succeeding. Also noteworthy: the first stuck run turned out to correspond to the *previous* (docs-only) commit, not the fix commit — a push during an in-flight deployment doesn't reliably trigger its own new run, so if "ship it" ever seems to hang, check `gh run list --json headSha` to confirm which commit the in-progress run actually corresponds to before assuming your own push triggered it.
